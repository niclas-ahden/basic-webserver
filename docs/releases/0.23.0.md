# basic-webserver 0.23.0

This release adds ES256 and RS256 signature checks to `Crypt`. They are
additions, so applications on 0.22.0 upgrade without source changes.

## Highlights

- **ES256 and RS256 signature checks.** `Crypt.verify_es256!` checks an ECDSA
  P-256 / SHA-256 signature and `Crypt.verify_rs256!` an RSA PKCS#1 v1.5 /
  SHA-256 one, the algorithms behind WebAuthn passkeys and many JWTs and signed
  webhooks. `Crypt.valid_es256_key!` and `Crypt.valid_rs256_key!` check a key
  ahead of time by the same rules. A malformed key or signature is a signature
  that does not hold, not a crash.
- **No new dependencies.** The checks run on `ring`, which already provides the
  platform's TLS.

## Upgrading from 0.22.0

Use the same Roc compiler as 0.22.0, commit `4b7b125`, which `flake.lock` pins.
No existing API changes.

## The checks

```roc
holds = Crypt.verify_es256!({ public_key, message, signature })
holds = Crypt.verify_rs256!({ modulus, exponent, message, signature })
takes_key = Crypt.valid_rs256_key!({ modulus, exponent })
```

`message` is the signed bytes themselves, which each check hashes with SHA-256.

ES256 takes the key as an uncompressed SEC1 point on P-256 (`0x04` followed by
the 32-byte x and y, as a JWK's `x` and `y` give them) and the signature
DER-encoded, as WebAuthn sends it. A JWS signature is the raw 64-byte `r` and
`s` instead, and has to be DER-encoded first. Compressed points and every other
key encoding are refused. A signature with a high S value holds, since ECDSA
does not require signers to normalise it.

RS256 takes the modulus and exponent as big-endian unsigned integers, as a COSE
key or a JWK's `n` and `e` hold them. The modulus is 2048 to 8192 bits and the
exponent is odd and from 3 to 2^33 - 1. 2048 bits is a security floor: shorter
keys can be factored with feasible effort, so they are refused even with a
correct signature.
